# Plan: Epoch AI sources and `entities suggest` (Phase 2 source, Phase 3 start)

Status: APPROVED · 2026-10-06

## Goal

1. Add two Epoch AI sources, both CC BY 4.0 and **Latest-only**:
   - `epoch_benchmarks`: "Capabilities & benchmarking" (`https://epoch.ai/data/benchmark_data.zip`):
     the Epoch Capabilities Index (ECI) per model and per-benchmark scores per model version.
   - `epoch_models`: "Data on AI models" (`https://epoch.ai/data/ai_models.zip`): publication
     date, organisation, parameters, training compute and accessibility per model.
2. Map Epoch models to canonical models in `config/entities/models.yaml` (`aliases.epoch`), so
   ECI joins LiteLLM prices. This becomes the first part of `cachereg entities suggest`
   (PLAN §4.3, Phase 3), which absorbs `scripts/suggest_model_aliases.py`.
3. Prepare starter analysis (a), "cost of intelligence" (LiteLLM price history × Epoch capability
   scores), **without building it**. Done when a mart exposes ECI by canonical `model_id` and a
   test shows the join to `dim_model_alias` LiteLLM keys works.

Out of scope: the analysis (a) mart and receipt; `entities check`; any change to published
receipts (`open-middle`, `openrouter-wallet-share`); new dependencies (none are needed:
`zipfile`, `csv`, `io` are stdlib; polars, duckdb and pyyaml are already used).

## What was measured (2026-10-06)

- Both zips are served with `content-type: application/zip`, an `etag` and no version id.
  `benchmark_data.zip` is 2.3 MB (91 files), `ai_models.zip` 3.3 MB (5 files). Both include a
  `README.md` with the licence and citation.
- **benchmark_data.zip**
  - `benchmark_metadata.csv` (88 benchmarks): `benchmark, in_eci, source_file, score_column,
    scale, random_baseline, score_ceiling, release_date, superseded_by`. 61 have a `source_file`
    and `score_column`, and every listed column exists in its file. 27 have neither, so their
    per-benchmark CSVs (23 files) are present but not described. Score columns vary (`Best score
    (across scorers)`, `Score`, `Accuracy`, `% Resolved`, …), and so do units (`scale` is a
    multiplier to 0–1: 1.0, 0.1 or 0.01).
  - Every per-benchmark CSV has a `Model version` column, and every version appears in
    `model_metadata.csv`.
  - `model_metadata.csv` (1,122 versions, plus empty rows): `model_version, model_group, date,
    display_name, organization, country, accessibility, training_compute_flop`. Versions are API
    ids with an optional reasoning-effort suffix: `claude-sonnet-4-5-20250929`,
    `claude-sonnet-5-5_max`, `gpt-6.1-sol_max`, `claude-opus-4-5-20251101_16K`, and host prefixes
    (`chutes/…`, `accounts/fireworks/models/…`). Suffixes seen: `high, unknown, low, none, medium,
    xhigh, max, minimal, <n>K, 0`.
  - `epoch_capabilities_index/eci_scores.csv` (274 models): `Model, Display name, eci,
    eci_ci_low, eci_ci_high, date, Organization, …, model_versions`. `Model` always equals a
    `model_group` (274/274), and `model_versions` was empty in every row.
- **ai_models.zip**: `all_ai_models.csv` (3,626 models, 57 columns, `Model` unique) is a superset
  of `notable_ai_models.csv` (1,078), `frontier_ai_models.csv` (138) and
  `large_scale_ai_models.csv` (532). 225 of the 274 ECI models appear by name in
  `all_ai_models.csv`; the misses are dated or preview variants (`Gemini 2.5 Flash (May 2025)`).
- **Name bridge to LiteLLM.** After stripping only the effort suffix and host prefix, 735 of
  1,122 versions are LiteLLM keys (bare, or as the last path part of a provider-prefixed key).
  208 of 274 ECI models have at least one such version. Through existing `models.yaml` LiteLLM
  aliases, 105 ECI models resolve to exactly one canonical model (42 of the top 50 by ECI), and 6
  are ambiguous (e.g. `GPT-5` → `openai/gpt-5` and `openai/gpt-5-chat`).

## Design

### 1. Two sources, not one

Each dataset has its own citation, and the chart footer credits a source by its registry
`attribution`, so a chart that uses only ECI should not credit "Data on AI models". The datasets
are also used independently: analysis (a) needs only `epoch_benchmarks`. The shared zip handling
(download, validation, reading) lives in `src/cachereg/sources/_epoch_zip.py`.
It is a helper inside `sources/`, not core, and the registry ignores it because it has no
registry entry. Core is not edited.

Registry entries (`config/sources.yaml`):

| field | `epoch_benchmarks` | `epoch_models` |
|---|---|---|
| history | native (same convention as `openrouter_rankings`, see below) | native |
| revisions | revised (updated in place, no history) → **Latest-only** | revised → Latest-only |
| redistribution / derived_charts | allowed-with-attribution | allowed-with-attribution |
| attribution | `Epoch AI, ‘Capabilities & benchmarking’ (epoch.ai/benchmarks), CC BY 4.0` | `Epoch AI, ‘Data on AI models’ (epoch.ai/data/ai-models), CC BY 4.0` |
| cadence | weekly | weekly |
| requires | [] | [] |

`history: native` + `revisions: revised` is the registry's existing convention for a source whose
whole dataset is downloadable on every fetch but revised in place, with past states kept only as
local vintages (`openrouter_rankings` is registered the same way; PLAN §4.4's table lists Epoch
as Latest-only). `snapshot` would make it Author-only, which is wrong: a replicator's own fetch
covers every model and date, only the values may have been revised since. SOURCE.md says so in
these words rather than calling the dataset a downloadable revision history.

Cadence is weekly: Epoch updates several times a week, but analysis (a) does not need daily
vintages, and every fetch stores the full zip (see §2).

### 2. Fetch (`_epoch_zip.fetch_zip(source, url, required_members) -> RawFetch`)

1. `http.get(url, headers={"Accept": "application/zip"})`. The body is kept as served.
2. Validate before storing: `zipfile.ZipFile(io.BytesIO(body))` opens. Every name in
   `required_members` is present (`README.md`, `benchmark_metadata.csv`, `model_metadata.csv`,
   `epoch_capabilities_index/eci_scores.csv` for benchmarks; `README.md`, `all_ai_models.csv` and
   the three subset files for models). The sum of declared uncompressed sizes is ≤ 256 MB (zip
   bomb guard). No member name is absolute or contains `..`. Nothing is extracted to disk: stage
   reads members from memory.
3. **Every fetch stores the zip** as `<name>.zip`, with `vintage = {kind: "content_sha256",
   value: sha256(body)}`. There is no fetch-time de-duplication: `render.source_vintages` derives a
   run manifest's per-source `content_sha256` from the selected fetch's `manifest["files"]`, so a
   manifest-only fetch would record the hash of `{}` and break `reproduce` comparisons. Storing
   every fetch keeps core untouched; at weekly cadence that is about 290 MB a year of local raw
   zips. Staging de-duplicates instead (below). (`http.Response` does not expose headers, so the
   content hash is the vintage, as PLAN §4.4 allows: "response content hash otherwise". The etag is
   not recorded.)
4. `fetch(full=False, today=None)` keeps the common signature; `full` and `today` are unused,
   because the source has no history to back-fill.

### 3. Stage

Both stages read every fetch and parse each **distinct** content hash once. Each stage emits a
`vintages` table with one row per fetch: `fetch_id, fetched_at (timestamp UTC), fetch_date,
content_sha256, vintage_id` (`vintage_id` = the earliest fetch_id with that content hash, whose
rows are staged). Data tables carry `vintage_id`. A stored zip that fails validation
at stage time raises (raw is immutable, so it is a bug or corruption, not a skip).

**`epoch_benchmarks`** tables:
- `models`: `vintage_id, model_version, model_group, release_date (Date), display_name,
  organization, country, accessibility, training_compute_flop (Float64)`. Rows whose cells are all
  empty are dropped silently (blank lines upstream; not a data problem, so not counted).
- `eci`: `vintage_id, model_group, display_name, eci, eci_ci_low, eci_ci_high (Float64),
  release_date, organization, country, accessibility, accessibility_group`.
- `benchmarks`: `benchmark_metadata.csv` typed (`in_eci` Boolean, numbers Float64, dates Date),
  plus `vintage_id`.
- `scores`: long format, one row per published score row: `vintage_id, benchmark,
  model_version (null when Epoch lists a row without one), row (1-based data row in the file),
  row_id (the file's `id` column if present), score (Float64, as published), scale,
  score_norm (= score × scale), score_column, source_file`. (Measured 2026-10-06: `scale` is a
  multiplier, values 1.0, 0.1 and 0.01; e.g. Aider's `Percent correct` has scale 0.01, and
  score × scale lies in 0–1 for every row. 1,085 rows repeat a (benchmark, version) pair: separate
  agents, scaffolds or runs, e.g. Terminal Bench lists several agents per model. All rows are
  kept; choosing one per model is an analysis decision, documented there.) Only benchmarks whose metadata names
  a `source_file` and `score_column` are read; the column is chosen by the metadata, never by
  guesswork. If a listed file or column is missing, staging raises. Non-numeric or empty scores
  are dropped; the non-empty non-numeric ones are counted in the source's **single**
  `_rejected_rows` table (the build's existing convention: `build._stage` reads one count per
  source from a table named `_rejected*` and `cli build` warns when it is non-zero). Empty cells
  are normal in multi-score files and are not counted. A non-empty non-numeric ECI value or a
  `model_metadata` row with an empty `model_version` but other cells set counts in the same table.
- Undescribed per-benchmark files are ignored and listed in SOURCE.md as a known gap.

**`epoch_models`** table `models`: from `all_ai_models.csv` with a fixed column subset:
`model, organization, publication_date (Date), domain, task, parameters (Float64),
training_compute_flop (Float64), training_compute_cost_2023_usd (Float64),
model_accessibility, open_model_weights, country, base_model, frontier_model, notability_criteria,
confidence, last_modified`, plus Booleans `in_notable`, `in_frontier`, `in_large_scale`
(membership by `Model` name in the subset files) and `vintage_id`. Dates such as `2023` or
`2023-07` are parsed to the first day of the period, with a `publication_date_precision` column
(day/month/year). Numeric cells that fail to parse become null and are counted in the
source's single `_rejected_rows` table (cells, not rows, for this source; SOURCE.md says so).

### 4. Marts (read only the vintage chosen by `<source>_cutoff`)

`build.cutoff()` already gives Latest-only sources the latest fetch date on or before as-of (or
the earliest, flagged). Each mart picks **one vintage**: the `vintage_id` of the latest fetch
(by `fetched_at`) whose `fetch_date` ≤ `<source>_cutoff`. Rows dated after as-of are dropped
(PLAN §4.4: observations ≤ as-of). A partial date counts from the **end** of its period (a
`2023` publication date is visible only from 2023-12-31, `2023-07` from 2023-07-31), so a model
is never visible before it could have existed; SOURCE.md records this. (All dates were
day-precision on 2026-10-06; the rule covers the format the files allow.)

- `020_epoch_capabilities.sql` (`-- inputs: epoch_benchmarks`):
  - `epoch_eci`: model_group, eci and its interval, release_date, organization, accessibility,
    `model_id` (via `dim_model_alias` source `epoch`, null when unmapped), vintage_id.
  - `epoch_scores`: scores joined to `models` (model_group, release_date) and `benchmarks`
    (in_eci, random_baseline, score_ceiling), with `model_id`.
  - `epoch_alias_coverage`: one row per measure: share of ECI models mapped, share of the top 50
    by ECI mapped (PLAN §4.3 coverage, target ≥95% for what an analysis uses).
- `021_epoch_models.sql` (`-- inputs: epoch_models`): `epoch_ai_models` at the chosen vintage,
  with `model_id` via the same alias table.

The analysis (a) mart (prices × ECI over time) is **not** built here. A test builds
`openrouter_rankings` + `litellm_prices` + `epoch_benchmarks` (the existing synthetic fixture plus
a synthetic Epoch zip; `epoch_benchmarks` + `litellm_prices` alone would leave mart 010 partial
with `litellm_prices` unused, which `build()` rejects) and proves the path `epoch_eci.model_id → dim_model_alias
(source litellm) → stg_litellm_prices_prices` returns a price for a synthetic model
(`lp_price_intervals` belongs to mart 010, which needs `openrouter_rankings`, so it is not used).

### 5. Entities: `aliases.epoch` and `cachereg entities suggest`

- **Alias semantics.** `aliases.epoch` lists Epoch **model groups** (the ECI `Model` /
  `model_metadata.model_group` / `all_ai_models.Model` name, e.g. `Claude Sonnet 4.5`).
  Versions (`claude-sonnet-4-5-20250929_16K`) reach their group through the staged `models`
  table, so they need no aliases. Reasoning-effort settings are a `variant` of the group's
  scores, kept in `epoch_scores.model_version`; ECI is per group. One Epoch group maps to one
  canonical model (the existing uniqueness check in `build._model_alias_frame` enforces it).
- **New module `src/cachereg/entities.py`** with:
  - `suggest_openrouter(...)`: the logic of `scripts/suggest_model_aliases.py`, moved unchanged
    (same rules, output and `--min-share`). The script is deleted; PLAN and the models.yaml header
    point to the command.
  - `suggest_epoch(...)`: reads the staged `epoch_benchmarks` (newest vintage) and
    `litellm_prices.prices`, plus `models.yaml`. For each **ECI** model group not yet mapped, in
    ECI order. (Groups without ECI are left alone: on 2026-10-06 most were raw version names or
    moving aliases such as `glm-4.7-flash_none` or `Qwen Plus (…)` → `qwen-plus`, and the coverage
    measure is defined on ECI.) Groups named after one host's run (`chutes/…`) are unresolved.
    1. `base(version)`: remove an **effort suffix** matching
       `_(none|minimal|low|medium|high|xhigh|max|unknown|\d+[kK])$` and keep only the **last path
       segment** (host or provider prefixes such as `chutes/`, `zai-org/`,
       `accounts/fireworks/models/`), then lowercase (the collapses PLAN §4.3 allows). Nothing
       else is stripped: dates, versions and quantisation suffixes are kept (`-20250929`, `-0528`,
       `-q8_0`; `_0` is not an effort setting).
    2. **Rule E1, existing model:** the canonical models whose `litellm` aliases contain a key
       equal to `base` or ending in `/<base>`. Exactly one model → propose `epoch: [group]` there.
       Several → report as ambiguous with the candidates; nothing is written.
    3. **Rule E2, new model:** no existing model, but LiteLLM keys match. Propose a new entry
       whose `model_id` is `<author>/<name>` from an `openrouter/<author>/<name>` key among the
       matches, if any; otherwise the group goes to the unresolved queue (no invented ids). The
       `litellm` list is that key plus the vendor's own matching keys (bare, or the vendor's
       LiteLLM prefix from the openrouter rules), dated before undated; resellers' keys
       (`azure/`, `deepinfra/`, …) and free-tier keys are never listed.
    3b. **Rule E3, review only:** when no key is owned, a group whose base matches exactly one
       canonical model once date suffixes and "."/"-" are ignored (`claude-opus-4-5-20251101` vs
       `anthropic/claude-opus-4.5`) is printed as a candidate and queued, **never written**: dates
       are not stripped automatically (PLAN §4.3), so a person confirms each one and adds it as a
       `# manual` alias. E3 is checked before E2, so a known model is not duplicated.
    4. A canonical model receives at most **one** Epoch group (otherwise one model would carry two
       ECI rows); a second claimant is unresolved.
    5. Otherwise: unresolved, written to `data/entities/unresolved_epoch.csv` (gitignored) with
       group, versions, ECI and organisation.
    It prints each proposal with its rule and ECI rank, then the coverage before and after.
  - `--write` is **comment-preserving**: new models are appended (as now), and an `epoch:` list
    is inserted under an existing model's `aliases:` block by a line-level edit. That edit is
    verified: the file is re-parsed and must equal the old mapping plus exactly the proposed
    aliases. Otherwise it aborts without writing.
- **CLI:** `cachereg entities suggest --source openrouter|epoch [--write] [--min-share F]`.
  `entities check` stays "not yet" (Phase 3).
- **Review:** proposals are reviewed by hand before committing `models.yaml`; ambiguous groups
  and confirmed E3 candidates get `# manual` entries with the reason, and wrong E1 matches are
  left out. Only `epoch` aliases are added to existing models (never `litellm` keys), so mart 010
  and the published receipts are unaffected. The goal is that the top 50 ECI models with a LiteLLM
  price resolve. Coverage is reported, not forced to 95% in this step.

## Tests (synthetic fixtures only)

Synthetic zips are built in the tests with `zipfile`; no recorded Epoch files.
1. Fetch: a valid zip is stored with its content-hash vintage. A zip missing a required member, with a `..` member or exceeding the
   size cap raises before anything is written. `http.get` is monkeypatched.
2. Stage benchmarks: the score column is the one named in metadata (a decoy column with a similar
   name is ignored); `score_norm = score × scale`; empty cells are skipped and non-numeric
   ones counted in `_rejected_rows`; a missing listed column raises; blank `model_metadata` rows
   are dropped; three fetches with two distinct contents give three `vintages` rows and two data
   vintages.
3. Stage models: subset flags, partial dates and their precision, numeric parsing.
4. Marts: with two vintages fetched on different days, `as_of` between them selects the first;
   rows released after as-of are excluded; `model_id` comes through `dim_model_alias` source
   `epoch`; the coverage table counts mapped and unmapped groups; the price join path to LiteLLM
   resolves.
5. Entities: effort suffix and host prefix stripped while a date suffix is kept; E1 unique,
   E1 ambiguous (not written), E2 with and without an `openrouter/` key; the comment-preserving
   writer keeps comments and refuses an edit whose re-parse differs; `suggest_openrouter` gives
   the same proposals as the old script on the existing synthetic fixture.
6. Existing tests keep passing. `test_build_sources_scope` (tests/test_pipeline.py) hard-codes the
   mart lists (`marts_skipped == ["005_openrouter_tokens", "010_openrouter_usage"]`); adding marts
   020/021 changes them, so step 3 updates those assertions in the same commit (scoped builds
   compare against the marts their sources select; the empty-scope case lists every mart from
   `load_marts()`). Published receipts are not re-rendered.
7. Stage benchmarks also: `score_norm = score × scale` (a 0.01-scale percent column); duplicate
   (benchmark, version) rows are both kept with distinct `row`; a row without a version is kept
   with a null `model_version` and excluded by the `epoch_scores` join.
8. Models mart: a year-precision `2026` row is excluded for as_of 2026-06-30 and included for
   2026-12-31; a month-precision row likewise against the month's last day.

## Risks

- **Upstream format drift** (columns renamed, files moved): staging raises with the file and
  column named, rather than silently mis-reading. The fixed column lists make drift visible.
- **ECI re-fitting**: cost-of-intelligence over time must say that capability scores come from one
  vintage of the index (Latest-only), while prices are Exact by date. Recorded in SOURCE.md for
  analysis (a)'s README.
- **Alias errors**: E1 and E2 only propose; nothing fuzzy is auto-accepted (PLAN §4.3). The
  ambiguous list is reviewed by hand.
- **Storage**: about 5.6 MB per fetch (both zips); weekly that is about 290 MB a year of raw
  zips, local only. Staged tables hold every distinct vintage; acceptable now, and
  stage can be limited to recent vintages later if needed.
